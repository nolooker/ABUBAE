# Admin 공지사항 관리 설계

## 목표

Master가 `/admin/notices`에서 공지를 작성·수정·게시하고, 방문자는 홈페이지에서 최신 공개 공지 3개를 확인한 뒤 상세 페이지를 열 수 있게 한다.

## 범위

- `/admin`의 `블로그/공지 관리` 카드를 `/admin/notices`에 연결한다.
- `/admin/notices`에서 공지 목록, 공개 상태, 작성일, 수정 진입점을 제공한다.
- 새 공지는 제목, slug, 본문, 공개 여부를 입력한다.
- 기존 공지는 같은 항목을 수정하고 공개·비공개로 전환한다.
- 홈페이지에는 `type = 'notice'`, `is_published = true`인 최신 공지 3개를 표시한다.
- 공지 상세 주소는 `/notices/[slug]`로 한다.
- 삭제, 이미지 첨부, 리치 텍스트, 예약 게시, 고정 공지는 이번 MVP에서 제외한다.

## 권한과 데이터 흐름

- 공개 홈페이지와 상세 페이지는 게시된 공지만 서버에서 조회한다.
- 비공개 공지는 공개 경로에서 존재 여부도 노출하지 않는다.
- `/admin/notices`와 작성·수정 API는 로그인한 `master`만 접근한다.
- 브라우저 입력은 서버에서 다시 검증한 후 Supabase에 저장한다.
- 서비스 역할 키는 서버 전용 코드에서만 사용하고 브라우저에 전달하지 않는다.

## 입력 규칙

- 제목은 공백 제거 후 1~120자다.
- slug는 소문자 영문, 숫자, 하이픈만 허용하며 1~120자다.
- 본문은 공백 제거 후 1~20,000자다.
- slug는 전체 `posts` 테이블에서 고유해야 한다.
- 공지 생성 시 `type = 'notice'`, `is_premium = false`로 고정한다.
- 수정 시 `updated_at`을 갱신하고 낙관적 잠금으로 오래된 편집을 거부한다.

## 화면

### 관리자 목록

- 제목, slug, 공개 상태, 수정일을 표 또는 모바일 카드로 표시한다.
- `새 공지 작성`과 각 행의 `수정` 버튼을 제공한다.
- 공개·비공개 상태를 명확한 배지로 표시한다.

### 작성·수정

- 제목, slug, 본문, 공개 여부 필드와 저장·취소 버튼을 제공한다.
- 저장 중 중복 제출을 막는다.
- 검증 오류, slug 충돌, 동시 수정 충돌, 서버 오류를 구분해 안내한다.
- 저장 성공 후 관리자 목록으로 이동하고 성공 메시지를 표시한다.

### 공개 화면

- 홈페이지에는 최신 공개 공지 3개의 제목과 작성일을 표시한다.
- 공지가 없으면 빈 상태 문구를 표시한다.
- 상세 페이지에는 제목, 작성일, 본문을 표시한다.

## 단계별 검수

1. 공지 테이블 보강, Master API, 테스트 공지 생성·조회 검증
2. `/admin/notices` 목록·작성·수정 검증
3. 홈페이지 최신 3개와 상세 페이지 검증
4. 공개/비공개 전환, slug·동시 수정 오류, 비회원 접근 검증

## 테스트

- 데이터 검증과 저장소의 공개/관리자 조회 범위를 단위 테스트한다.
- API의 401, 403, 400, 404, 409, 성공 응답을 테스트한다.
- 관리자 폼의 저장·오류·중복 제출을 컴포넌트 테스트한다.
- 홈페이지 최신 3개 정렬과 비공개 제외를 테스트한다.
- 자격증명이 있는 테스트 환경에서 작성→공개→홈페이지 확인→수정→원복 E2E를 수행한다.
